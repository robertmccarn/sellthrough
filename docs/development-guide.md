# Development Guide

SellThrough is a learning-first data project. The codebase should teach the
shape of a small production-minded ETL system while still staying simple enough
to reason about locally.

## Documentation Rules

- Document intent, data flow, and tradeoffs whenever a new feature changes how
  data is extracted, transformed, stored, or presented.
- Add inline comments for API-specific behavior, schema choices, normalization
  rules, scoring formulas, error handling, and anything that would be hard to
  rediscover from the code alone.
- Avoid comments that merely restate syntax. For example, explain why a retry
  policy exists, not that a function calls `session.get()`.
- Keep design documentation close to the implementation. Use `docs/` for
  system-level notes and module docstrings for local architecture notes.

## Folder Hygiene

- Commit source, docs, examples, and intentionally curated fixtures.
- Do not commit secrets, `.env`, local SQLite databases, generated caches,
  virtual environments, build artifacts, or package metadata generated by local
  installs.
- Prune local generated files after verification when they are not needed for
  ongoing work. The project should stay easy to scan from the root folder.

## Current Architecture Principles

- `src/sellthrough/config.py` owns environment-based configuration and redacted
  diagnostics.
- `src/sellthrough/db.py` owns the local SQLite schema and database bootstrap.
- `src/sellthrough/ebay/` owns eBay API clients. Browse is for active listings,
  Marketplace Insights is for sold-item history, and Taxonomy is for category
  normalization.
- `src/sellthrough/cli.py` owns top-level CLI assembly. Command-specific parser
  and handler logic lives under `src/sellthrough/cli_commands/`.
- Raw API responses should be stored before normalization so future transform
  logic can be replayed and audited.
- Active polling reads watchlist rows, saves raw Browse responses, transforms
  raw Browse payloads into stable rows, and upserts normalized
  `active_listings`; see `docs/active-polling-design.md`.
- Lookup commands read normalized tables only. Sold lookup metrics should remain
  explicit as pending until Marketplace Insights data is available.

## Feature Addition Checklist

Before calling a feature done:

- Add or update design notes when the feature introduces a new workflow,
  external API, schema, or metric.
- Add comments for non-obvious learning points and implementation tradeoffs.
- Keep commands documented in the README or an appropriate doc file.
- Run the smallest useful verification command.
- Remove generated clutter that is not meant to remain in the working folder.
